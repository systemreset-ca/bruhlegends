## Verified function facts

All new functions: owner `postgres`, `SECURITY DEFINER = true`, `search_path = pg_catalog`.

- EXECUTE granted to `service_role`, denied to `anon`, `authenticated` and `PUBLIC`:
  `bruh_account_tip_read`, `bruh_account_tip_reserve`, `bruh_account_tip_find_request`,
  `bruh_account_tip_cancel`, `bruh_account_tip_finalize`, `bruh_secure_action_setup_begin`,

  `bruh_account_tip_authorized_read`, `bruh_account_tip_authorized_signed`.
- `bruh_account_tip_signed(uuid,bigint,text,text,bigint)`: EXECUTE false for `service_role`, `anon`,
  `authenticated` and `PUBLIC` — the unrestricted foundation signer is reachable only from inside the
  authorization wrapper.

## Known limitations

- Every managed object is owned by the shared `postgres` superuser role, which can alter or drop any of
  these objects; the deny grants constrain application roles, not the platform owner.
- The platform `sandbox_exec` role holds BYPASSRLS and read ACLs, so forced RLS does not hide these rows
  from platform-level administration.
- Shared-worker encrypted custody remains in force: there is still no isolated signer runtime, no reset,
  export, withdrawal or retirement flow, and no mainnet activation.

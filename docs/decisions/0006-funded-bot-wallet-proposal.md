## Proposed experience

Verified Telegram identity → provision embedded BRUH wallet → show deposit address/network → confirmed deposit → display spendable balance → user authorizes a Telegram tip → protected signing/broadcast → server confirms exact on-chain transfer → group-scoped receipt/statistics/participation. Withdrawals return funds to a user-selected, verified destination. Balance must distinguish confirmed funds, reserved outgoing funds and pending transfers.

Do not put private keys in bot messages, Supabase application rows, source, logs or ordinary configuration secrets. Evaluate managed embedded-wallet signing with isolated key infrastructure, user recovery/export through an authenticated wallet flow, scoped/revocable application authorization, spending limits and step-up approval for withdrawals/key export. Never export a key into Telegram chat. A provider-specific design and threat model are still required.

Earlier managed-provider suggestions were rejected by the owner. Build a separately controlled BRUH signer; do not introduce Privy/Turnkey dependency or create paid accounts as an assumed requirement.

## Security model change

If BRUH can authorize transactions without a separate user-held wallet signature, it has meaningful spending authority. Managed key storage does not by itself make that authority non-custodial. The original no-server-signing invariant must be replaced by an explicit reviewed authorization policy before enabling this architecture; do not silently label it unchanged or retain inaccurate public non-custodial claims.

Retain server-verified Telegram identity, per-group attribution/isolation, canonical network/mint controls, recipient/amount/reference verification, immutable audit events, RLS and controlled sensitive writes. No cross-group wallet fallback. Whether provisioned wallet identities remain per-group or become a separately consented user-level account requires an explicit decision; preserve current isolation until resolved.

Require authenticated command intent, replay/idempotency protection, atomic outgoing balance reservations, concurrent-spend defenses, fee estimation, transaction recovery/reconciliation, withdrawal takeover controls and a signer kill switch. Never mark pending deposits spendable or tips confirmed solely because signing/broadcast succeeded. A Telegram account/session compromise is part of the threat model.

Only ephemeral in-memory keys have been generated by isolated cryptographic tests; no live user wallet or stored production key has been created or collected. No provider account, signing authorization, deposit custody, mainnet or real-funds feature is enabled. First implementation must use devnet and pass wallet/custody security review. Fees, tokenomics and points rules remain unapproved. User recovery/control, signer policy, isolated signing host/key-management configuration and the operational/compliance responsibilities of the chosen authority model remain decisions before activation.

## Implemented first slice

`custody-vault.server.ts` provides AES-256-GCM envelope encryption, random per-wallet seed/data key/IVs, authenticated wallet/group/membership/network/version binding, non-extractable wrapping-key requirement and rotation without changing wallet identity. It exposes no raw-key import/export or generic transaction-signing API. It is not wired to the bot or any HTTP route. Memory zeroing is best effort, not a guarantee against process compromise.

The proposed SQL core creates group-scoped devnet accounts (frozen initially), encrypted envelopes, immutable receipts and atomic fee-inclusive tip reservations/settlement accounting. No client or existing service role can read envelopes or execute custody writes; grants require the future reviewed signer/verifier roles. SQL proof parameters come from a future trusted chain verifier; SQL itself is not an on-chain verification implementation. Timer expiry does not release ambiguous spending holds.

Migration is proposed only and is not in the applied Drizzle journal. Do not apply or activate it until the signer/verifier, user authorization, passkey step-up, durable signed-transaction recovery and reconciliation are implemented. Existing external-wallet operations remain active in the meantime. No new funding address or custodial marketing claim should be issued yet.
